---
title: "Update Workspace"
api: "PATCH /v7/:projectId/workspaces/:id"
description: "Edit a workspace's name and metadata"
---

Edits a workspace's own `name` and/or `metadata`. Gated by the `edit-workspace` capability (or owner).

<Note>
  This does **not** flip `inheritsFromParent` — that is a separate [owner-only action](/api-reference/workspaces/update-inherit-flag).
</Note>

## Path Parameters

<ParamField path="id" type="string" required>
  The workspace UUID.
</ParamField>

## Body Parameters

<ParamField body="name" type="string">
  New display name. 1–100 characters.
</ParamField>

<ParamField body="metadata" type="object">
  New metadata (opaque JSON).
</ParamField>

<ParamField body="actingUserId" type="string">
  Service/master keys only — the user to act as. **Not enforced on this endpoint yet** (see the warning below).
</ParamField>

<Warning>
  **`actingUserId` is not enforced on this endpoint yet.** The guard on this route resolves authority *after* the master/service-key bypass, so for a key the named user is never looked up. The call runs with **full owner authority regardless of who you name** — including a user with no standing on this workspace at all. Naming a non-owner will **not** stop the call — the `edit-workspace` capability check is skipped for a key whether or not the named user holds it. The value is **discarded entirely** — it is not read, not stored, and not carried on any webhook, so it is not an audit trail either. Gate the call in your own backend. Enforcement — binding a key to the named user's real authority — lands in a follow-up change.
</Warning>

## Response

Returns the updated [Workspace](/data-models/workspace) object.

## Error Responses

<AccordionGroup>
  <Accordion title="Unauthorized — 403">
    ```json
    { "error": "You do not have the edit-workspace capability.", "code": "workspace/unauthorized" }
    ```
  </Accordion>
</AccordionGroup>
